# RowHammer: заметки по эксперименту с памятью Linux

## Что хотел проверить

Мне было интересно, насколько заметно меняются данные от нескольких одиночных битовых ошибок. Взял область оперативной памяти, задал известный шаблон и проверял содержимое и SHA-256 до и после контролируемого воздействия. Здесь не нужна отдельная программа с правами root.

**Важная деталь:** программа выполнялась в настоящей среде Linux. Зафиксированные изменения в этой серии получены *программным введением ошибок в выделенный буфер*; это не подтверждение физической уязвимости установленных чипов DRAM. Сам эксперимент позволяет проверить механизм фиксации повреждений и их последствия.

## Окружение

Debian GNU/Linux 13 (trixie), ядро `6.18.57`, Python `3.13.5`, архитектура x86-64. Размер страницы Linux — 4096 байт. Для снимков терминала использовались `xterm` и виртуальный X-сервер.

## Идея проверки

Выделил через `mmap` 24 КиБ. Условно разделил область на три части по 8192 байт: два крайних участка с `0x55` и центральный участок с `0xAA`. Центральную область (`victim`) считывал и сравнивал с исходным состоянием. Соседние виртуальные адреса здесь не означают соседние строки DRAM, поэтому это удобная схема для проверки целостности, а не полноценное аппаратное hammering-испытание.

```text
+----------------------------+
| область A: 8192 Б / 0x55   |
+----------------------------+
| область victim: 8192 Б     |  <-- сравнение и SHA-256
| исходное значение: 0xAA    |
+----------------------------+
| область B: 8192 Б / 0x55   |
+----------------------------+
```

В разных сценариях использовал условное число активаций как параметр нагрузки. После выбранного порога код целенаправленно меняет отдельные биты в `victim`, а затем измеряет число изменившихся битов и байтов. Порог не измерялся у аппаратного DRAM-контроллера.

## Как запускал

```bash
python3 --version
uname -r
python3 rowhammer_experiment.py --csv results.csv
```

## Что получилось

| Сценарий | Условных активаций | Изменённых битов | SHA-256 совпадает |
|---|---:|---:|:---:|
| Контроль | 0 | 0 | Да |
| Одна сторона | 60 000 | 0 | Да |
| Две стороны | 25 000 | 0 | Да |
| Две стороны | 60 000 | 1 | Нет |
| Две стороны | 100 000 | 3 | Нет |
| Две стороны | 150 000 | 5 | Нет |
| Две стороны + условная защита | 150 000 | 0 | Да |

При трёх изменениях (`double_100000`) некоторые байты исходного `0xAA` превратились в `0xA8`, `0xBA` и `0x2A`. Уже единичной инверсии достаточно, чтобы SHA-256 контрольного участка перестал совпадать с исходным. Повторный запуск даёт те же результаты, поскольку места программной инъекции задаются детерминированно.

## Что вынес из этого

- Изменение небольшого числа битов заметно влияет на целостность массива данных; для обнаружения достаточно сравнить буфер либо его контрольную сумму.
- SHA-256 выявляет отличие данных, но не препятствует RowHammer и не восстанавливает повреждённые значения.
- Условный сценарий обновления строк полезен для сравнения с защитой, но по нему нельзя оценивать эффективность настоящего TRR.
- Для снижения риска реальных аппаратных ошибок нужны прошивки и механизмы контроллера памяти, корректные refresh/TRR/RFM, поддерживаемая ECC-память, аппаратная диагностика и резервное восстановление.

## Границы результата

`mmap` работает с виртуальными адресами Linux и сам по себе не раскрывает расположение физических DRAM-строк. Здесь не выполнялся аппаратный тест с проверкой подлинных `ACTIVATE/PRECHARGE`. Зафиксированные битовые инверсии внесены программной операцией XOR. Поэтому результаты описывают *потерю целостности при введённых ошибках*, а не найденную физическую уязвимость конкретной планки памяти.
